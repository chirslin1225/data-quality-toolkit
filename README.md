# data-quality-toolkit

A small, dependency-free Python tool that scores the quality of a tabular dataset and reports **where the defects are and what they cost** — rather than just counting them.

Most data-quality libraries report one number per rule ("1,204 missing values"). That is not useful when one missing timestamp can break a downstream pipeline while one missing marketing tag costs nothing. `dqkit` lets you assign a **relative error cost** to each defect type, so the score reflects operational impact, not raw defect volume.

```
$ python -m dqkit examples/sample_sensor_data.csv
```

```
# Data Quality Report — `examples\sample_sensor_data.csv`

Rows: 5,038   Columns: 8

## Score: 70.3 / 100

_needs targeted repair before it feeds a model_

| Rule | Column | Count | Rate | Cost | Burden |
|---|---|---:|---:|---:|---:|
| missing | `pressure_kpa` | 412 | 8.18% | 3.0 | 0.25 |
| constant | `firmware` | 5,038 | 100.00% | 0.1 | 0.10 |
| duplicate | `*` | 38 | 0.75% | 1.0 | 0.01 |
```

Note the ordering: the single most expensive row is not the largest count. `firmware` touches every row but costs almost nothing to fix, so it sits below 412 missing pressure readings — which are what would actually break a downstream model.

## Quickstart

```bash
git clone https://github.com/chirslin1225/data-quality-toolkit.git
cd data-quality-toolkit
python -m dqkit examples/sample_sensor_data.csv
```

No dependencies. Python 3.9+.

Run the tests:

```bash
python -m unittest discover -s tests -v
```

Regenerate the synthetic dataset at a different size:

```bash
python examples/make_sample.py --rows 20000
```

Skip metadata columns you do not want scored:

```bash
python -m dqkit examples/sample_sensor_data.csv --ignore device_id,firmware
```

## How the score works

For every finding, the tool computes a **burden**:

```
burden = defect_rate × error_cost
score  = 100 × exp(-Σ burden)
```

`error_cost` defaults are in `dqkit/score.py` and can be overridden with `--costs my_costs.json`:

```json
{ "missing": 3.0, "duplicate": 1.0, "gap": 4.0 }
```

The exponential form means the score never goes negative, falls steeply for the first few serious defects, and flattens out as defects accumulate — which matches how data actually fails in practice: one broken join hurts more than ten cosmetic gaps.

## What is implemented

- [x] `missing` — empty or whitespace-only cells
- [x] `duplicate` — duplicate rows across all columns
- [x] `constant` — columns with a single distinct value
- [x] cost-weighted scoring
- [x] Markdown report
- [x] synthetic sample data with injected defects

## Roadmap — open tasks

These are the parts that need domain judgement, so they are left as stubs with docstrings describing the intended behaviour:

- [ ] `dtype` — check each column against a declared schema (type conformance), reporting the first offending value per column
- [ ] `gap` — irregular sampling in a timestamp column: find intervals greater than `expected_interval × tolerance`, and report how many expected samples are missing
- [ ] `outlier` — robust IQR-based outlier detection per numeric column, with a configurable fence
- [ ] `uncertainty` — the score above is a point estimate over the whole file. For very large files, compute it from a sample and report a confidence interval (bootstrap over rows). This is the question that matters most: *how sure am I that this dataset is good enough to ship?*

See `dqkit/checks.py` for the stubs.

## Sample data

`examples/sample_sensor_data.csv` is **synthetic** — generated by `examples/make_sample.py` with known, injected defects so the report has something to find. A stereo-vision-inspired sensor schema was chosen because timestamp misalignment across modalities is a realistic and expensive failure mode. No real or company data is included anywhere in this repository.
